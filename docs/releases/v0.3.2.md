# DisplayWeave v0.3.2

Release date: 2026-10-26. **Stable release**, Mac build / Android version code **21**. Reviewed native source: `b01e1326263a537f1f7fee9ea13282fdfb39e77e`; source PR #22 merged as `1bfa1ca`. The previous stable release was v0.3.1 (20). Releases publish directly as stable versions without public preview, beta or RC stages.

## Changes

- Add iMac 4K (4096×2304), 4.5K (4480×2520) and 5K (5120×2880) desktop presets. At Retina 2×, 5K provides a 2560×1440-point desktop. Existing saved modes keep their meanings.
- Replace the ambiguous Native label with **Match receiving screen**, showing actual logical dimensions. Show desktop points/backing pixels separately from encoded video size, with fullscreen guidance on both Macs.
- Move potentially blocking VideoToolbox submissions off the capture/control queue to a serial encoder worker with at most two retained submissions. Encoder creation, changes and retirement share its ordering; stale generations cannot update a replacement session. Intermediate 40/50 FPS also use the two-frame encoding pipeline.
- Enable **Adapt Mac encoder load** by default. Three measured overloaded active windows are required; idle/sparse animation and network backlog do not cause a downgrade. Resolution priority preserves detail and lowers FPS; frame-rate priority reduces video size first. Neither changes desktop/window layout. Five healthy active windows and at least 30 seconds allow recovery, with backoff after failed recovery. The setting can be disabled and is excluded from bitrate benchmark mode.
- Bound capture updates to five seconds, clear cached old-size frames and handle stop, replacement, codec fallback, errors and late completion. Failure stops the affected session with reconnect/disable-adaptation guidance.
- Add negotiated desktop/codec and average encode-submission/pressure diagnostics. Android and iOS retain their v0.3.1 behavior and receive matching versioned packages.

The [iMac report](../verification/imac-resolution-performance.md) records log evidence, regressions and physical acceptance separately. The supplied log supports encoder pressure during active windows; it does not establish that every stall has the same cause.

## Recommended iMac settings

Update both Macs. Select **Match receiving screen**, use fullscreen on the receiver, and match the macOS display scaling on both computers. For smoother dragging/scrolling, select **Frame-rate priority** and leave **Adapt Mac encoder load** enabled. For text detail, use **Resolution priority**. Reducing video quality can lower load without rearranging the desktop.

A receiving window scales the entire desktop to fit. A 3840×2160 Retina desktop has only 1920×1080 logical points and can enlarge windows on a 5K screen. The new 5K desktop mode does **not** enable 5K video: the Apple decoder envelope remains 4096×2304 landscape / 2304×4096 portrait. No 4K/5K60 or dual Intel iMac performance guarantee is made.

## Compatibility and signing

GPL-3.0, upstream attribution, project/bundle/package identities, existing preference values, Bonjour, framing, pairing, Sparkle key and Android certificate are preserved. The new adaptation preference defaults on; existing desktop selections are retained. Mac signing continuity was verified against the exact downloaded v0.3.1 ZIP (build 20), including designated requirement, team, bundle ID and universal architectures. Build 20 → 21 privacy-permission continuity was not interactively retested.

**Mac remains Apple Development signed and unnotarized.** Use the [installation and permission guide](../guides/mac-permissions.md) if macOS blocks opening. Android retains its original project certificate. iOS is an unsigned arm64 re-signing input requiring the user's valid Apple identity. Downloads use GitHub Releases; update metadata uses project GitHub Pages.

Regressions include the original iMac geometry/cadence failures, sustained-load policy, bounded concurrency, stale replacement, codec fallback, stop, update failure/timeout and late completion.
- Local Thread Sanitizer, actual Apple↔Java TLS, Mac/iOS Keychain and secure Android runtime passed. Secure iOS passed an isolated rerun; the initial background-listener check failed and its log is retained. iOS source was not changed.
- With an independent built-in display online, real AppKit window/fullscreen/lifecycle and three 1×/2× virtual-display create/remove cycles passed. On arm64/macOS 26.5.2, three isolated synthetic 4K probe runs each encoded 180/180 frames at approximately 60 FPS. New-worker callback latency was about 13.99 ms median / 14.71 ms p95. A prior contended run dropped 84/180 frames and is explicitly retained as non-comparable evidence.
- Build 21 universal Mac Release ZIP/DMG, hardened runtime/nested signatures and baseline continuity, Android Release certificate, unsigned arm64 iOS identity/hygiene, bundle/feed versions and six file hashes passed. Independent CryptoKit Ed25519 verification passed against the unchanged embedded Sparkle public key. Packaging reran the seven Android Java test groups.

Local evidence: `artifacts/verification/imac-resolution-2026-10-26/` and `artifacts/verification/v0.3.2/`. Final publication/CI receipts are recorded in [the checklist](release-checklist.md).

## Physical verification still required

The reporter described both machines as approximately 2019 Intel iMacs. Exact CPU/GPU/OS and receiver fullscreen state are unconfirmed. Actual dual-iMac latency, scaling, adaptation/recovery, both directions on Ethernet, sleep/wake, energy usage and endurance remain pending. Synthetic arm64 tests and Intel compilation do not prove Intel driver performance. See the [reproduction procedure](../verification/imac-resolution-performance.md).

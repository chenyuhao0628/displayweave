# Mac 与 Mac 局域网显示设计

设计日期：2026-10-15。基础版本：DisplayWeave `1dbfb48`。

执行 `git merge-tree --write-tree main origin/main`，未改动工作区或索引。
共同祖先为 `99c342c`；双方分别有 165 / 100 个独有提交。上游改动
145 个文件，与本项目重叠 21 个，试合并产生 20 个冲突文件。

## 用户目标与范围

- 任一 Mac 可作发送端或接收端；每次只启用一种角色。
- 同一局域网，通过 Wi-Fi 或以太网自动发现并连接。
- 发送支持镜像和扩展；接收支持窗口、全屏及选择显示器。
- 首版两端均为 macOS 14+，以 H.264、60fps 为上限进行兼容性验证。
- 接收 Mac 显示发送 Mac 的桌面，由发送 Mac 的键鼠操作。
- 原有 iPhone、iPad、Android 连接与更新功能继续有效。

本次不实现同时双向串流、跨机键鼠、音频、文件传输、互联网穿透、
雷雳专用路由或 macOS 12/13 接收包。4K/5K 显示器会按解码上限缩放；
60fps 是配置目标，不是未经真机验证的性能承诺。

## 架构与文件边界

`Mac/Receiver/StreamReceiver.swift` 移植上游接收核心，负责 TCP、封包、
H.264 解码、视频层、光标及遥测；只编译进 Mac 目标，避免改变现有 iOS 接收器。
`Mac/Receiver/ReceiverWireProtocol.swift` 保留上游消息定义。
`Mac/Receiver/MacReceiverController.swift` 管理接收实例、屏幕、窗口和睡眠恢复。
`Mac/Receiver/ReceiverVideoView.swift` 是承载视频层与光标的最小 AppKit 视图。
`Mac/MacRoleController.swift` 协调角色；SwiftUI 负责设置与状态，AppKit 负责视频窗口。
`Mac/MacReceiverPolicy.swift` 隔离可测试的面板、分辨率和会话策略。

发送链路：虚拟屏/主屏 → ScreenCaptureKit → VideoToolbox → TCP。
接收链路：TCP → 有界拆包 → Annex B → CMSampleBuffer → AVSampleBufferDisplayLayer。

## 角色与生命周期

启动默认发送模式；保存用户明确选择的模式。接收监听仅在接收模式启用。
切换过程禁用重复操作：停止发送会话和发现任务，释放虚拟屏后启动接收；
反向切换先停止接收监听与视频窗口，再恢复发送发现。

发送发现过滤本机 install ID；收到本机 hello 也必须终止自连接。
取消角色时，晚到的网络/ADB 回调不得恢复连接。关闭接收视频窗口明确结束
当前会话并返回等待状态；关闭控制窗口保持后台服务，退出应用则释放全部资源。
接收端休眠停止监听、发送结束消息；唤醒后恢复监听，允许用户重新连接。
会话重建必须清空解码器、光标和缓冲区，旧连接回调不得影响新会话。

## 协议兼容

保留 `_opensidecar._tcp`、TCP 9000、4 字节大端长度前缀、JSON 控制消息与
Annex B 视频。Mac 接收端通过 `device=Mac` 标识身份，声明面板与解码能力。
同时提供本项目旧字段与上游 `pv`、`videoCaps`、`panel` 字段。
Mac 始终使用 Apple 传统视频封包，不因上游 `pv=3` 启用 Android DWV2。

发送器对 Mac 单独协商 H.264、帧率与最大尺寸；尊重解码宽高、像素吞吐量和
显示刷新率，避免 5K H.264 超限。用户的全局 HEVC/120fps 设置不能越过 Mac
接收能力。iOS/Android 现有策略保持原有语义。`streamConfig` 同时携带
`fps` 和 `framesPerSecond`；退出识别 `closing`、`sleeping` 与 `goodbye`。

面板策略区分像素与点，Mac 的非 Retina 面板可使用 1x，Retina 使用 2x；
改变流分辨率不改变桌面逻辑坐标。物理尺寸使用桌面默认值，避免手机尺寸。
切换接收屏幕/显示模式后重新公告，发送端按新的面板参数重建扩展显示。

## 连接与边界

接收模式由用户主动开启；一个接收端一次服务一台发送 Mac，忙碌时拒绝
额外连接，用户可先断开。Bonjour 网络不通时显示本地网络权限与防火墙提示。
界面将网络传输标为局域网（Wi-Fi/以太网）。

现有链路为无加密、无身份认证的 TCP，仅用于可信局域网；接收模式界面明确
展示这一边界。开启接收表示允许局域网发送端连接，不伪装成已配对认证。
首版不暴露远程关机功能。帧长度与缓冲区有上限，错误输入关闭当前连接并
继续监听。只接收画面时不要求屏幕录制或辅助功能权限。

## 实施顺序

1. 保存上游合并评估、设计与验收标准。
2. 先增加失败的能力协商、面板、生命周期和封包边界测试，再实现策略。
3. 移植接收核心并加入有界输入、状态隔离与稳定停止逻辑。
4. 实现窗口、屏幕选择、全屏、睡眠、断开与角色互斥。
5. 接入发送器能力协商、面板缩放与关闭消息兼容。
6. 更新双语用户文档、来源说明、构建入口和 CI 自检清单。
7. 运行 Swift 策略及网络接收集成测试、macOS/iOS 构建、Android 和网站回归。

## 验收标准与证据

- 两角色切换不会同时监听和发送，不接受本机连接。
- Mac H.264 分辨率/帧率不越过声明能力；传统 iOS 和 Android v2 自检继续通过。
- 接收 TCP 能处理拆包、粘包、非法长度、断连重连和过期回调。
- 窗口显示、关闭、全屏与屏幕选择有明确行为，接收模式不显示发送权限请求。
- Mac 构建通过；iOS 与 Android 原有构建/测试和双语文档检查通过。
- 必须区分本机自动验证与双 Mac 真机证据。没有第二台 Mac 时，不宣称
  已通过双机 60fps、Wi-Fi/以太网、30 分钟或 2 小时耐久验证。

实施和验证结果在用户指南及最终交付说明中记录；本设计不把未执行的真机
项目标记为完成。

## 实施结果

开发实现和本地验证于 2026-10-16 完成，证据及剩余实体设备矩阵见
[使用指南](mac-to-mac.zh-CN.md)。角色协调核心和 SwiftUI 界面分别位于
`Mac/MacRoleController.swift` 与 `Mac/MacRoleViews.swift`，前者可注入服务并测试
异步清理期间的互斥性。接收端使用 macOS 14+ 的 `sampleBufferRenderer` 在串行
队列上提交视频；不引入上游远程关机、直连线缆探测或 iOS 重构。

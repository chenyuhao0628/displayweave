# Mac 4K 延迟：源码改动与本机证据

日期：2026-10-23。已包含在 [v0.3.0 正式版（19）](../archive/releases/release-notes-v0.3.0.zh-CN.md)，原生源码为 `929eb93`。本文记录本机证据，不保证 Intel 设备达到 4K60。

## 范围与实现

保留所选的 3840×2160 桌面/编码分辨率、编码偏好和 60 FPS 目标。本次针对两台 Intel iMac 经以太网连接时，发送端鼠标不跟手的反馈。提供的成功会话已请求低延迟 H.264 和独立光标传输。编码器启动回退、首帧失败及采集/显示器恢复现已在后续[上游集成](../archive/audits/upstream-integration-2026-10-23.zh-CN.md)中实现。

- 60 FPS 时允许两帧编码在途，与已有的 90/120 FPS 策略一致。异步完成超过 16.7 ms 时，单槽位会不必要地跳过隔帧采集。上限仍为两帧；编码器过慢时仍实施背压。
- 光标改用独立的交互优先级队列，每 8 ms 采样；最多一个传输写入在途，加一个可替换的最新位置。移除归一化坐标 0.0004 的移动门槛，相当于 4K 下约 1.5 个水平像素。沿用现有认证 TCP 连接及分帧格式；尚未发送的光标消息使用高于视频的相对优先级。不能越过已提交的 TCP 字节。
- 接收端主线程繁忙时，只提交最新光标位置。光标图片也合并待处理工作；会话替换后拒绝旧投递令牌和图片代际。
- Mac 视频及接收处理使用交互 QoS；发送端增加与接收端一致的 interactive-video 网络服务类别。两端原本已启用 TCP no-delay；接口绑定保持原有行为。
- 记录实际路径接口类型、编码器属性/查询结果、采集/编码/发送速率、编码提交阻塞，以及光标合并/主线程等待。新增 Mac 接收端统计回传到发送端，使既有日志能包含两端情况。这些诊断不新增桌面像素、按键、光标坐标或私有对端身份。

`EnableHardwareAcceleratedVideoEncoder` 显式优先选择硬件，但不强制 H.264 必须使用硬件。硬件可用、请求属性和编码器创建成功，均不等于证明实际使用了哪个编码器。不支持的属性查询记录为 unknown。

## 自动验证

| 测试 | 修改前 | 修改后 |
| --- | --- | --- |
| 60 Hz 下 600 次采集，模拟 19/23/28 ms 异步完成 | 接纳 300 帧 | 接纳 600 帧 |
| 主线程阻塞时经真实回环 TCP 接收 240 条光标消息 | 恢复后执行 240 次回调 | 仅执行最新位置的 1 次回调 |
| 传输完成回调阻塞，光标继续采样 | 原先没有光标写入预算 | 一个写入在途，保留最新待发采样 |
| 替换会话后旧工作才完成 | 新增回归覆盖 | 不消耗或取消新会话工作 |

另一项真实回环测试通过生产写入器和分帧解析器，并发发送 48 个按序的 256 KiB 视频载荷及高优先级光标消息，分帧和视频顺序保持正确。

帧率表是确定性的调度模型，**不是屏幕实测 FPS**。回归测试先在旧策略/投递代码上失败，再验证修复。55 组 Swift 测试包括真实 Mac 接收端 TCP/TLS、非法帧、重连、输入授权及新增光标/诊断用例。Mac Debug 可编译 arm64 与 x86_64。通用架构编译不会执行 Intel 驱动。

光标投递/采样回归也通过 Thread Sanitizer 检查，未报告数据竞争。

运行 `./tools/run-swift-self-tests.sh`，以及[开发指南](../development/workflow.zh-CN.md)中的不签名通用架构构建。可选的 `python3 tools/run-mac-4k-probe.py` 会编译有界离屏探针，每组编码 180 帧合成移动方块画面，尺寸 3840×2160、H.264、60 FPS 目标、49,766,400 bps 目标码率。对比旧的一帧预算/零帧延迟与生产代码的两帧预算/一帧延迟策略。添加 `--bitrate-mbps 100` 可测试 100 Mbps 目标。不使用屏幕采集、虚拟显示器、GUI 窗口或用户偏好设置。

在本机 **arm64 / macOS 26.5.2** 上，两组均编码 180/180 帧，约 60 FPS，没有失败或跳帧。该主机的回调能在一个 60 Hz 帧间隔内完成，因此本机没有表现出帧率提升。`MaxFrameDelayCount` 和 `PrioritizeEncodingSpeedOverQuality` 返回不支持属性状态（-12900）；硬件查询返回 unknown。这些结果只说明本机合成负载的表现，不代表复杂桌面渲染、接收端显示或 Intel 性能。

补充的 100 Mbps **目标码率**探针，两组同样编码 180/180 帧，无跳帧或失败：旧策略约 60.02 FPS，新策略约 60.04 FPS；仍返回相同的不支持属性结果。这验证简单合成场景下的编码配置，不代表实测吞吐达到 100 Mbps，也不测量以太网容量。该轮延迟优化的 55 组回归、不签名 Mac 通用架构构建、93 对双语文档、发布链接及空白检查均通过。后续上游集成已通过 60 组测试及新一轮不签名 Mac 通用架构构建。独立测试编译仍有既有的 CVDisplayLink 弃用警告；Mac 应用构建无警告。

## 第二轮：保守限制与恢复策略审计

第二轮源码核对复现了四处限制：

| 路径 | 原行为 | 源码调整 |
| --- | --- | --- |
| 编码提交 | 支持该属性的编码器在 `MaxFrameDelayCount = 0` 时，必须先输出第 N 帧，第 N 帧提交调用才能返回；只放宽外部编码并发不能消除这个串行约束。 | 60/90/120 FPS 的两帧预算匹配 `MaxFrameDelayCount = 1`；30 FPS 保留零。继续启用实时编码、禁用 B 帧，同时记录请求值和属性状态。 |
| Mac 渲染器占用 | 每次观察到暂时不能接收更多帧，就清空解码器并丢弃后续依赖帧，等待关键帧。 | 从首次繁忙起 50 ms 内，最多允许额外两帧；超出后只清空一次，等待恢复可接收并收到关键帧。真正的解码失败仍走原有失败/回退路径。 |
| Mac 自动码率 | 本地发送拥塞可降低码率，恢复逻辑却仅在手机 `stats` 处理器中；Mac 接收端不发送此消息。 | Mac 会话启用本地恢复：有视频活动且发送无积压持续五秒后，上调 7%，最多恢复原目标。空闲窗口、超过一秒的采样中断和手动模式不作为恢复证据；手机接收端策略继续独立处理。 |
| Apple 配置帧率 | `exactFrameRate` 将已协商的 90/120 FPS 写成 60。 | 保留协商值，范围仍为 1…120。这修复配置一致性，不放宽 4K 解码能力上限，也不能解释 60 FPS 会话的卡顿。 |

四项新增回归均先在修复前失败。在模拟完成时间 19/23/28 ms 下，零帧延迟要求的提交模型接纳 300/600 次采集；有界并行模型接纳 600/600。模型验证的是 API 的提交约束，不是 Intel 实测吞吐。接收端回归将真实编码的 H.264 I/P 帧经回环 TCP 送入生产解析代码，用可控渲染器复现短时/持续积压、50 ms 上限、关键帧恢复、会话替换和失败状态；不模拟物理显示时序。码率回归原先从 50 Mbps 降到 44 Mbps 后不再恢复，现在可恢复到 50 Mbps 且不超过原目标。

Apple API 语义已核对本机 SDK 的 `AVQueuedSampleBufferRendering.h`（暂时不可接收是占用反馈，允许有界提交）和 `VTCompressionProperties.h`（提交延迟及码率约束）。额外两帧/50 ms 是有界的源码策略，实际延迟效果仍待实机验证。

其余限制及用户要求的码率调整核对如下：

- Apple 的 `4096 × 2304 × 60` 像素/秒上限允许日志中的 3840×2160/60 和 4096×2304/60。HEVC 同时满足 H.264 能力范围，是为了保留同分辨率的可解码回退。
- TCP 的以太网与 Wi-Fi 共用名为 `wifi` 的历史码率策略类别。按用户要求，v0.3.0 将 H.264 局域网上限从 60 提高到 100 Mbps，开放手动 80/100 Mbps，非 Benchmark 模式仍限制到 100 Mbps。此调整适用于该局域网策略下的所有接收端，不仅是 Intel Mac。4K60 清晰模式自动起始估算仍约为 49.77 和 56.62 Mbps；放宽上限不会强制这些会话使用 100 Mbps，也不能证明帧率提升。新增预设/截断回归先在旧 60 Mbps 限制下失败。参见[码率模式](../reference/bitrate-modes.zh-CN.md)。
- 一秒窗口的硬性 `DataRateLimits` 上限与平均目标码率相同。SDK 指出目标过于接近硬上限可能导致实际码率偏低。增加突发余量属于后续编码器/画质实测候选，尚未在缺少负载及链路速率证据时启用。
- 采集队列深度八、视频发送预算、单个光标写入加最新待发位置、帧大小校验、会话代际和编解码限制仍保持有界。没有证据就提高这些上限，可能只是增加排队工作。

## 诊断与待完成的实机验证

- `TRANSPORT-PATH`：已建立路径使用以太网还是 Wi-Fi；不测量网线链路速率，也不能证明物理直连拓扑。
- `ENCODER-IMPLEMENTATION`：可查询时的硬件/编码器身份，以及部分属性请求状态码。
- `PIPELINE-STATS`：约两秒窗口内的采集、编码、发送速率，丢帧、在途工作、实测吞吐、最近一次发送完成延迟和最大同步编码提交耗时。
- `CURSOR-SEND`：位置变化、合并、完成次数，采样间隔和完成延迟；活动时约两秒记录一次。
- `MAC-RECEIVER-STATS`：接收端送入渲染器的速率、解码背压 flush 次数及容忍提交的帧数、光标接收/应用/合并数量及本地主线程最大等待时间。不等于物理屏幕 FPS 或同步测量的单向延迟。
- 后续新增 `ENCODER-ATTEMPT` 及实际模式日志、`FIRST-VIDEO-TIMEOUT`、`CAPTURE-RECOVERY`、`CAPTURE-SOURCE-MISMATCH`、`DISPLAY-UNIT-RECOVERY`，区分启动拒绝、无视频、恢复等待、采集错屏和显示器编号冲突。

**SKIP：**两台 macOS 15 Intel iMac、真实直连网线吞吐、4K 屏幕采集及可见渲染、长时间延迟/稳定性。本机没有这两台受影响的 Intel 设备；未运行屏幕采集、窗口或虚拟显示器测试。未重启 WindowServer 或远程访问服务。

共享 TCP 中已经提交的视频字节仍可能延后光标；Network.framework 的发送完成也不是远端显示确认。独立光标采样不保证 120 Hz 显示，也不能消除所有网络/解码延迟。独立传输协商及保证达到 4K60 的工作点仍不在本次改动范围内；编码器初始化回退已在所链接的上游集成中实现，并用注入失败测试覆盖。打包后，优先用用户日常 4K 场景做一次简短确认并收集增强后的发送端日志，避免反复排列组合编码和分辨率。

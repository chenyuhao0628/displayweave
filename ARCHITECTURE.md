# DisplayWeave Architecture

## System shape

DisplayWeave consists of a macOS sender and Apple/Android receiver applications. The Mac creates a virtual display with `CGVirtualDisplay`, captures it with ScreenCaptureKit, encodes it with VideoToolbox, and sends framed video over a direct local TCP connection. Input and receiver telemetry travel back on the same session.

Each connected device owns an independent sender pipeline and benchmark recorder. Runtime bitrate changes update VideoToolbox rate-control properties without rebuilding the encoder. Auto bitrate consumes per-session queue, drop, RTT, and frame-age evidence; send-queue and GOP policies remain bounded by quality and transport. Target bitrate is configuration intent, while actual bitrate is measured throughput.

```text
macOS virtual display
  -> ScreenCaptureKit (video + opt-in 48kHz PCM/Opus system audio over UDP/TCP on source branch)
  -> VideoToolbox H.264 / negotiated HEVC
  -> framed mutual-TLS TCP control & fallback session (legacy plaintext is explicit)
  -> optional authenticated udpMediaV1 Wi-Fi/LAN media, cursor & audio plane (source branch)
     -> iOS/iPadOS receiver (usbmuxd USB or WiFi, negotiated HEVC/H.264)
     -> Mac receiver (LAN / pinned direct-link interface, HEVC/H.264)
     -> Android receiver (ADB-forward USB, source-branch AOA 2.0 USB, or WiFi, HEVC/H.264)
  <- touch, scroll, stylus, consented desktop input, codec status, metrics, lifecycle messages
```

## Discovery and identity

Apple and Android WiFi receivers advertise the inherited `_opensidecar._tcp` Bonjour/NSD service for compatibility. An install ID identifies a receiver application instance across transports. Compatibility names such as `OpenSidecar.xcodeproj`, bundle IDs, Java package names, preference keys, and service names are migration-sensitive contracts, not current public branding.

## Android USB

In `v0.3.5` downloads (and on the source branch whenever wired ADB is online), the Mac locates ADB from an explicit preference, `PATH`, Android SDK environment variables, the default macOS SDK, or Homebrew. It parses `adb devices -l` and admits only rows in `device` state with wired `usb:` metadata. Wireless-debugging endpoints are excluded.

For every wired serial, the Mac allocates an unused loopback port and runs:

```text
adb -s <serial> forward tcp:<dynamic-local-port> tcp:9000
```

Each `DeviceSession` owns and removes only its own mapping. DisplayWeave never uses `adb forward --remove-all`. USB reuses the normal framed protocol, stream configuration, codec negotiation, input, and metrics path.

On the **source branch (not yet in published `v0.3.5` downloads)**, DisplayWeave adds a zero-ADB user-space **Android Open Accessory (`AOA 2.0`)** transport (`AndroidUSBFunction`, `AccessoryDeviceWatcher`, `USBAccessory` / `AccessoryRelay` on Mac; `UsbAccessoryReceiverTransport` + `Composite` on Android):

- **Interface-gated probing and deterministic ADB arbitration:** `AccessoryDeviceWatcher` matches only Android `.adb` (`0xFF/0x42/0x01`) or `.mtp` USB interfaces (rejecting docks, cameras, MIDI devices, and Apple peripherals), probes `GET_PROTOCOL` at most once per `IOUSBHostDevice` registry entry, and defers USB probing while `adb` claims a serial online (`AndroidWiredArbitrationPolicy` prefers online `adb` `device` rows and surfaces actionable recovery guidance when `kIOReturnExclusiveAccess` `0xE00002C5` indicates an unauthorized/offline `adb` daemon or MTP file-transfer app holds the interface).
- **16 KiB URB framing, ZLP handling, and mutual TLS:** After switching the phone to accessory mode (`0x18D1:0x2D00`/`0x2D01`, `manufacturer = "OpenDisplay"`, `model = "OpenDisplay Receiver"`, GitHub-only `releaseURI`), `AccessoryRelay` and Android `UsbAccessoryReceiverTransport` exchange `16 KiB` (`16,384 B`) bulk IN/OUT transfers with packet-aligned bulk OUT zero-length packets (`byteCount % maxPacketSize == 0 && byteCount % 16384 != 0`) and a `64` consecutive empty-read bound (ZLP != EOF), bridging over `127.0.0.1` into `UsbmuxTLSRelay` + `AppleTLS` + `AppleSecureAdmission` (`DWA1`/`DWR1`) and Android `SecureSocketAdmission` mutual TLS by default. `UsbAccessoryReceiverTransport.Composite` keeps TCP port `9000` (ADB/Wi-Fi) and AOA active simultaneously without monitor lock-order inversion, closing only the superseded transport on USB↔Wi-Fi handover, while `SenderController` tracks non-persistent `accessoryFallbackSuppressedSerials` so dismissed USB permission prompts fall back to same-ID Wi-Fi without re-dial oscillation until unplug or manual reconnect.

## Auto handover

Auto prefers USB. A protocol-level grace period and bounded 0.5/1/2/4/8-second recovery sequence run after failure. When exhausted, Auto may accept only the WiFi receiver with the same install ID. If USB returns, the same-install-ID WiFi session ends before USB connects, preventing the single-client Android receiver from being contested by two Mac sessions.

## Codec and frame-rate negotiation

Legacy Apple receivers use H.264. Android advertises codec and refresh capabilities, accepts `streamConfig`, and prefers HEVC when both sides support it. Codec failure produces a control message and falls back to H.264. Android negotiates 30/60/90/120fps targets and requests a compatible display mode; requested FPS is not proof of rendered FPS.

All peers retain the outer four-byte network-order frame length. Legacy iOS and non-negotiated Android frames use the JSON telemetry prefix plus Annex-B payload. Only Android peers that independently advertise `binaryFrameHeaderV2` receive the fixed `DWV2` identity/timestamp/flags header; the receiver then hands an offset/length view of the original bounded transport array to MediaCodec. See [the binary-header and allocation contract](docs/reference/android-binary-frame-header-v2.md).

## Lifecycle and input

The Android receiver owns a TCP server on port 9000 and restarts idempotently when the rendering surface returns. On reconnect, the Mac resends stream configuration before requesting a keyframe and treats a peer protocol message—not only TCP connect—as readiness.

Touch coordinates, drag state, cursor movement, and two-finger scroll are encoded as control JSON and injected on macOS. Accessibility permission is required for input injection.

## Security boundaries

- v0.3.5 defaults to certificate-pinned mutual TLS and explicit invitation pairing on Apple and Android. Legacy compatibility is an explicit unencrypted choice for trusted networks. See [pairing](docs/guides/secure-transport.md).
- ADB RSA authorization trusts the Mac as a debugging host beyond DisplayWeave.
- The macOS v0.3.5 release uses a pinned Apple Development identity and is not notarized. The first migration from an ad-hoc release may require reauthorization; later builds are checked for signing continuity.
- The Android APK uses an offline project keystore stored outside Git.
- The iOS public artifact is an unsigned re-signing input.
- `CGVirtualDisplay` is a private API and can change across macOS releases.

See [SECURITY.md](SECURITY.md) and [docs/README.md](docs/README.md).


## Mac receive role (experimental)

The Mac app switches between sending and receiving. Receiving stops sender sessions
and discovery, then uses an independent TCP listener, bounded deframing and
AVSampleBufferDisplayLayer H.264 / hardware-gated HEVC rendering. One sender is accepted at a time; stale
connection callbacks cannot mutate replacement sessions. The sender respects logical
points, display scale and codec size/fps limits. Mac uses legacy Apple framing, not
Android DWV2. See the [design](docs/reference/mac-to-mac-design.md).

## Source ownership and bounded work (2026-10-16)

The source app supports exclusive Mac send/receive roles over the same Wi-Fi or Ethernet LAN. This is packaged as an experimental feature in v0.3.5; physical acceptance remains pending. Mirroring captures an existing display; extending creates a virtual display.

| Area | Ownership |
| --- | --- |
| Mac presentation | `OpenSidecarMacApp`, `MacRoleViews`, `SenderWorkspaceView`, `SenderSettingsView`, `SessionRow`, `UpdateViews`; `SettingsWindow` narrowly hosts the desktop settings window. |
| Mac sessions | `SenderController` owns discovery and replacement barriers; each `DeviceSession` owns a sender and `SessionLifetime`. Startup failure and stop release resources before a replacement starts. |
| iOS presentation | `ReceiverScreen`, `ReceiverIdleView`, `ReceiverOnboardingView`, `ReceiverSettingsView`, `ReceiverPerformanceView`, `ReceiverModel`, `ReceiverVideoView`. |
| Shared Apple boundaries | `Shared/ReceiverFrameDecoder` validates legacy lengths (16 MiB maximum); `ReceiverCursorImage` checks bytes and pixel geometry before decoding; `BoundedLogWriter` limits files and queued work. |
| Android presentation | `ReceiverUi` owns shared styles; `MainActivity` owns connection/lifecycle presentation. |
| Website | Shared CSS tokens and semantic React sections; server rendering and client hydration share the same tree, with generated bilingual-page checks. |

`PhoneReceiver` owns listener/connection state on its serial queue and ignores stale callbacks. Backgrounding detaches the old socket before a best-effort goodbye. Android control writes have one worker, 128 queued tasks and a 64 KiB payload limit; readers have two workers and two queued tasks. Saturation disconnects the affected session so input cannot accumulate without bound. Sender geometry and input are validated before arithmetic and CoreGraphics conversion.

See the [UI contract](docs/development/ui-guidelines.md), [development commands](docs/development/workflow.md), and [source audit with verification limits](docs/archive/audits/source-upgrade-audit-2026-10-16.md).

## HEVC, direct links and Pencil (source iteration)

Mac HEVC requires both a hardware encoder and an explicitly advertised hardware decoder. `ReceiverVideoBitstream` bounds NAL count and parameter sets; one codecFailure requests a timed H.264 fallback. HEVC raster/fps also satisfy a complete H.264 envelope. Invalid Mac capability envelopes are rejected before capture.

`DirectCable` classifies link-local wired **candidates**; it does not authenticate peers or prove physical topology. A selected candidate pins both Bonjour resolution and TCP to its interface. `DirectCableAutoConnectPolicy` implements default-off opt-in, one attempt per appearance and manual opt-out. Existing sessions are deduplicated by installation ID, including pending hello.

`pencil-v1` uses explicit hello/inputConfig negotiation. `PencilInputForwarder` fixes native/legacy mode for a whole stroke; `PencilSample` validates all numeric fields. `InputInjector` posts tablet point/proximity with deterministic cancellation. iOS `InputSendBudget` admits at most 64 queued/in-flight controls, each framed batch at most 64 KiB, before dispatch; connection epochs reject stale input and completions. An overflow closes that peer so sender cleanup releases held input. See the [protocol and acceptance plan](docs/reference/hevc-wired-pencil-plan.md).

## Apple video negotiation

Both Apple targets share `Shared/ReceiverVideoBitstream`. iOS advertises `appleVideoV1` codec/refresh envelopes; Mac recognizes its existing device identity. The sender uses bounded Apple operating-point negotiation up to 120fps and HEVC with H.264 fallback, while Android keeps its separate V2 negotiation. See [current implementation and evidence](docs/guides/apple-video.md).

## Completed source extensions

The [feature ledger](docs/archive/plans/feature-completion.md) records desktop resolution, default authenticated transport, consented Mac keyboard/mouse input, same-ID Mac handover, Pencil v2 and named shortcuts, process CPU sampling, Android pooled leases and shared protocol vectors. The iOS presentation owns callbacks by view identity: replacement retires old input before attachment, and late old-view teardown cannot clear new callbacks or remove a borrowed video layer. Decoder/presentation callbacks carry connection generations; cross-thread frame callbacks use locks. Actual production signing and final artwork remain external requirements.

## Desktop geometry and measured encoder load (v0.3.2)

Desktop points/backing pixels are separate from the encoded raster. iMac presets and receiver-matched geometry preserve the selected layout while video quality adapts. `EncoderWorkQueue` serializes VideoToolbox ownership away from capture/control, with at most two retained submissions. `EncoderLoadController` uses sustained active encoder pressure, excludes idle/network-limited windows, and follows the user's resolution/frame-rate priority. Capture reconfiguration clears cached frames, rejects stale generations and has a five-second deadline. See [the implementation and evidence](docs/verification/imac-resolution-performance.md); in v0.3.2–v0.3.5 downloads a 5K desktop does not expand the 4096×2304 Apple video decoder envelope (source-branch `hevc5kV1` adds hardware-gated 5120×2880@60 HEVC below).

## Automatic desktop matching (v0.3.3)

For Mac receivers, an eligible sender display and optional validated system-reported physical dimensions inform an estimated logical desktop. Missing sizes fall back to proportional matching; mobile receivers retain their existing geometry in v0.3.3–v0.3.5. Existing preferences are preserved. Screen changes are debounced and session-scoped, with cooldown and stale-state checks. In v0.3.3–v0.3.5 downloads the 4096×2304 Apple video envelope is unchanged. See [the matching evidence](docs/verification/automatic-desktop-matching.md).

## High-refresh trials, decoder recovery, and Android keep-alive (v0.3.4 – v0.3.5)

Android and eligible iOS/iPadOS receivers offer opt-in native-resolution high-refresh capability envelopes without expanding default conservative limits. On Android, `ReceiverKeepAliveService` promotes active sessions to a user-stoppable `connectedDevice` foreground notification and orders shutdown after foreground promotion so quick connection turnover cannot trigger `ForegroundServiceDidNotStartInTimeException`. `DecoderStallRecoveryPolicy` requests a fresh `streamConfig` (`streamConfigRequired`) on negotiated V2 sessions and recreates the `H264SurfaceDecoder` in place on legacy V1 sessions (`!negotiatedV2`), while `OpenDisplayServer.stop()` synchronizes with `decoderWorker` and releases `MediaCodec` asynchronously on a detached thread. All `OpenDisplayServer.Listener`, `NsdAdvertiser.Listener`, and `WifiTcpReceiverTransport` callbacks carry the originating source reference so retired instances cannot mutate active UI state. On iOS/iPadOS, `MetalVideoRenderer` guards texture commits across reset and generation epochs and caches `MTKView.drawableSize` without off-main-thread UIKit reads; Mac receivers gate window presentation and connection status on decoded `videoSize`. See [the v0.3.5 release notes](docs/releases/v0.3.5.md), [the v0.3.4 release notes](docs/releases/v0.3.4.md), and [Android decoder throughput and recovery](docs/reference/android-decoder-throughput-recovery.md).

## Low-latency media transport, `udpMediaV1`, and cross-platform upgrades (source iteration)

**Implemented (source branch, not yet in a published release download):**
- **Encoder VBV, settled crisp static refresh, speed priority, and TCP/UDP ABR coordination:** Runtime bitrate-only ABR updates modify VideoToolbox rate-control properties in place (`AverageBitRate` and a `50ms` `DataRateLimits` VBV burst ceiling of `[max(ceil(bitrate / 8 * 0.05 * 1.5), 16_384), 0.05]` — `1.5x` target bitrate over `0.05s` with a `16,384 B` floor) without emitting a new `streamConfig` or resetting the receiver decoder. `AdaptiveBitrateController` enforces a `1.0s` normal decrease hold and a `250ms` (`0.25s`) fast-drop hold on severe congestion spikes (`pendingSends >= 4`, `androidQueueDepth >= 4`, `androidCongestionDrops >= 3`, Wi-Fi `sentFps / encodedFps < 0.60`, or local `pendingSends > queueBudget` / `oldestPendingSendAgeMs >= 50`). While `udpMediaSession.isReady` is true, TCP `AdaptiveBitrateController` cuts are suspended so `UDPDelayGradientBWE` drives `streamBitrate` (applying `EncoderLoadController` ceilings via `updateEncoderLoadCeiling` without overwriting the pacer's pre-FEC wire budget), and `syncCurrentBitrate` hands the active bitrate back cleanly on UDP-to-TCP fallback. `NonBlockingUDPSocket.SendResult` distinguishes `.sent`, `.wouldBlock` (`EAGAIN`/`EWOULDBLOCK`/`ENOBUFS`), and `.failed` (with single `EINTR` retry) so `UDPMediaSenderSession` excludes unsent datagrams from `onBytesSent` and tracks up to `16` `incompleteVideoFrameIds` to prevent partial frames from reporting `completedFrame == true`. Sender throughput telemetry (`lastSentFps`, `lastActualBitrateMbps`, `onStats`) accounts uniformly across UDP and TCP; iOS receiver telemetry publishes every `1.0s` (measuring submission and backpressure latency on both Metal and `AVSampleBufferDisplayLayer` paths) to match Android and Mac. `CaptureFramePolicy` skips zero-dirty-rect static frames after the initial frame while enforcing a `500ms` refresh keep-alive, fires a generation-guarded `180ms` post-motion settled crisp refresh frame (`CaptureStaticFrameGate` + `SettledCrispRefreshEncoderPolicy`: temporarily applying `PrioritizeEncodingSpeedOverQuality = false`, `MaxAllowedFrameQP = 20`, and spatial quality `0.90`, then safely restoring `51` or an explicit `1...51` caller QP ceiling), converts `SCStreamFrameInfo.displayTime` Mach host time to capture timestamps, and bounds both capture FPS-cap updates and decoder-FPS downgrade updates (`decoderFpsAdjustmentTimeoutWork` + cancellation-responsive `awaitStreamConfigurationUpdate`) with `5s` timeout guards. `StreamEncodingPolicy.prioritizesEncodingSpeed(quality:fps:)` enables `PrioritizeEncodingSpeedOverQuality` only when `quality == .smooth` or `fps >= 90`. Android's pending frame queue is bounded to `4` frames / `75ms` (`FrameQueuePolicy`), and Apple receivers (`PhoneReceiver` and `StreamReceiver`) wire `ReceiverFrameAgePolicy` to drop non-keyframe TCP packets whose local queue age reaches `65ms` (`0.065s`) or synchronized sender-to-receiver age reaches `120ms`.
- **Authenticated `udpMediaV1` media plane (Wi-Fi/LAN):** mTLS TCP remains authoritative for pairing, control, keyboard/pointer/stylus input, cursor PNG sprites, all USB sessions, and pinned `DirectCable` wired links by default (`UDPMediaActivationPolicy`, overridable via `forceUDPMediaOnDirectCable`; whenever UDP is created on a pinned link, `IP_BOUND_IF` / `IPV6_BOUND_IF` binds the socket to that interface, with dual-stack IPv4/IPv6 support). Wi-Fi and unpinned LAN peers advertising `udpMediaV1` negotiate a session-scoped UDP plane (`UDPMediaProtocol`, `UDPMediaFEC`, `UDPMediaEngine`, `UDPMediaTransport`, `UDPDelayGradientBWE`, and Android `UdpMediaProtocol` / `UdpMediaReceiverSession`): `MacSender` sends `udpMediaConfig` after `streamConfig` (with monotonic `sessionEpoch` acceptance on both Apple and Android receivers and synchronized `OpenDisplayServer.UdpMediaLifecycleSlot` lifecycle management on Android so `udpMediaConfig` before or after initial `streamConfig` never tears down an active UDP session or leaks sockets), receivers send up to `6` initial UDP probes spaced by `150ms`, and `UDP-MEDIA-READY` triggers immediate (`<20ms`) static-screen IDR replay from `lastPixelBuffer` when needed. Each datagram carries a 16-byte header authenticated as AAD under AES-128-GCM with RFC 5869 HKDF-SHA256 directional keys, a 64-bit rollover counter (ROC), and a 1024-packet anti-replay window.
- **Pacing, multi-block FEC, NACK/RTX, jitter buffer, and delay-gradient BWE:** `UDPDebtPacer` paces outgoing packets on `1ms` ticks at `1.2x` pre-FEC target bitrate (`maxQueuedPackets = 2048`) with strict priority ordering (`cursor > audio > retransmit > keyframe > normalVideo > fecParity`), latest-wins cursor coalescing, a 16-packet audio queue cap, and wrap-safe stale P-frame purge on newer IDR arrival. `UDPMediaFECEncoder` generates multi-block (`<= 16` blocks × `<= 64` data shards, up to `15` parity shards/block) Cauchy/XOR Reed-Solomon parity over GF(256) (`0x11d`) and deducts FEC overhead from the encoder bitrate budget. Receivers leave total fragment count unset on parity-first arrival so multi-block (`> 64` fragments) frames never truncate, submit immediately when all data shards arrive, recover missing shards via Gaussian elimination, emit reorder-aware NACK bitmaps (Android receiver `RTT <= 80ms`, up to `2` NACKs/fragment; sender `UDPRetransmitCache` `RTT <= 60ms`, `8` frames / `512` packets / `80ms` max age, at most `1` retransmit/fragment), order frames in a 32-bit wrap-safe jitter buffer (Apple `UDPJitterBuffer`: `3` frames / `45ms` in `UDPMediaEngine`; Android `JitterBuffer`: `4` frames / `35ms`, dropping unreferenced P-frames across hold-deadline gaps until the next keyframe), ignore stale-`configVersion` UDP frames across live resizes, and report `5ms` burst arrival gradients every `30ms` to `UDPDelayGradientBWE` (`20`-sample trendline + AIMD). Unresponsive UDP paths (`2.5s` receiver silence while sending) fall back to TCP framing and request a recovery keyframe.
